# Pilot review: 2026-11-06

Four services reviewed against current vendor documentation. All four have
supported corrections and explicitly retained uncertainty. No matching
patterns, cookie lifetimes, categories, legal bases, placeholders or Consent
Mode flags were changed. No new translations were generated.

## Shared findings

The previous Google location text named only the USA and included a transfer
framework. Google's [privacy policy](https://policies.google.com/privacy) and
[transfer information](https://policies.google.com/privacy/frameworks) describe
worldwide processing. The three Google records now say `Worldwide`.
This avoids presenting a transfer mechanism as a storage location. Google's
framework page links its certification, but the registry detail page did not
expose readable status in this review. No finding of certification loss is
made; no renewed certification assertion is added.

The existing category, legal-basis and placeholder choices remain catalog
policy. They are not conclusions about what every website must do. Empty
storage lists are not evidence of absence of storage. Full browser tests and
CookieHold compatibility tests were outside this documentation review.

## google-tag-manager

Outcome: **corrected**, version 2 → 3, with unresolved findings.

### Evidence and changes

- `purpose` is now “Loads the site's other tags.” Google's
  [consent settings](https://support.google.com/tagmanager/answer/10718549?hl=en)
  describe optional per-tag checks; the old claim that every tag waits for
  consent was unconditional. Removed the second sentence from each existing
  locale's purpose, retaining its original first sentence and `machine` flag.
- Added the consent settings and
  [Tag Manager privacy page](https://support.google.com/tagmanager/answer/9323295?hl=en)
  to `sources`. The privacy page discusses diagnostic collection and request
  logs, so a container is not equivalent to no data exchange.
- The [installation guide](https://support.google.com/tagmanager/answer/14847097?hl=en)
  confirms `gtm.js` and the older `ns.html` snippet. It explicitly preserves
  the older installation. Both matches and the inline signature remain.
- Added the missing source for the existing Site Kit hint. The author-published
  [Site Kit entry file](https://plugins.svn.wordpress.org/google-site-kit/trunk/google-site-kit.php)
  and [GTM4WP entry file](https://plugins.svn.wordpress.org/duracelltomi-google-tag-manager/trunk/duracelltomi-google-tag-manager-for-wordpress.php)
  were readable, with versions 1.191.0 and 2.1.1 respectively. This verifies
  the plugin paths, not a guarantee that their configuration loads a container.
- Google describes [Consent Mode](https://developers.google.com/tag-platform/security/concepts/consent-mode)
  at the tag level. Retained the container's existing flags; its contained
  tags can have different behavior. The two guidance notes already capture
  initialization and per-tag review and need no additional filler.
- Provider and privacy URL remain. The policy applies to Tag Manager and
  [Google's affiliate list](https://business.safety.google/affiliates/)
  includes Google Ireland; this is weaker than a product-specific entity
  statement for every customer. Location changed as described above.

### Unresolved and impact

Confirm the provider against product-specific terms for the intended EU
audience; a corporate affiliate list alone does not establish all processing
roles. The empty cookie list is not a universal no-cookie guarantee: Google's
[cookie export](https://business.safety.google/static/assets/csv/adcookies.csv)
associates `_dc_gtm_<property-id>` with both Analytics and Tag Manager. Before
assigning it, establish whether it belongs to the container or a loaded
Analytics tag in supported integrations. No speculative ownership rule was
added. The purpose and location changes affect descriptions, not blocking.

## google-analytics

Outcome: **corrected**, version 3 → 4, with unresolved findings.

### Evidence and changes

- Added the [GA4 cookie guide](https://support.google.com/analytics/answer/11397207?hl=en):
  it supports the two GA4 identifiers and their recorded default lifetimes.
  These defaults are configurable and browser restrictions may shorten them.
- Downloaded Google's official
  [cookie CSV](https://business.safety.google/static/assets/csv/adcookies.csv)
  from its advertising-cookie page. It still lists `_gid` and `_gat` with the
  existing lifetimes. Retained those entries and legacy matches; their absence
  from the GA4-only table is not evidence that a mixed detection catalog
  should delete them. Added the CSV as primary evidence.
- The [tag setup guide](https://developers.google.com/tag-platform/gtagjs)
  supports the loader and collection hosts. It also explains that one Google
  tag can have multiple product destinations. Existing `gtag/js` matches and
  inline signatures remain unchanged.
- The [Consent Mode overview](https://developers.google.com/tag-platform/security/concepts/consent-mode)
  supports Analytics consent handling and advanced cookieless measurements.
  Added this source; existing flags and guidance remain.
- Added [regional collection documentation](https://support.google.com/analytics/answer/12017362?hl=en).
  Regional collection before onward processing does not mean data stays in
  that region. Location changed to `Worldwide`; provider and privacy URL remain.
- Retrieved all seven plugin entry files already linked in the service:
  Site Kit 1.191.0, MonsterInsights 11.3.0, ExactMetrics 10.3.0, Analytify 9.1.2,
  GA Google Analytics 20260810, Google Analytics for WooCommerce 2.4.4 and Rank
  Math 1.0.281. Paths exist. Analytify's entry file contains both current
  gtag.js and legacy analytics.js references, supporting retention of legacy
  detection. No compatibility claim follows from these checks.

### Unresolved and impact

The record is a multi-generation detection entry, not a GA4-only cookie list.
Keep that scope when displaying it. The broad shared Google tag loader may
represent destinations other than Analytics; narrowing it requires consumer
matching tests and a review of the Google Ads rules. Exact WordPress script
handles were not traced through every current plugin module and need a
separate source-level check before being called reverified. Google's
[controller terms](https://support.google.com/analytics/answer/9012600?hl=en)
identify Google Ireland for certain European data-sharing activities, but are
not a blanket statement of all roles under the base Analytics agreement.
Provider scope remains a documented limitation. No detection behavior changed.

## youtube

Outcome: **corrected**, version 3 → 4, with unresolved findings.

### Evidence and changes

- Google's [cookie explanation](https://policies.google.com/technologies/cookies)
  supports YSC's session duration and security role, and both recorded
  six-month identifiers. It describes replacement of VISITOR_INFO1_LIVE by
  __Secure-YNID while still discussing both names. Retained both for detection.
- [YouTube's embed guide](https://support.google.com/youtube/answer/171780?hl=en)
  and [IFrame API reference](https://developers.google.com/youtube/iframe_api_reference)
  support the two embed domains and iframe_api. Added these sources and the
  [developer policies](https://developers.google.com/youtube/terms/developer-policies).
  Existing privacy-enhanced guidance remains accurate and appropriately limited.
- [Google's regional provider FAQ](https://policies.google.com/faq?hl=en)
  supports Google Ireland for EEA consumer services. Added it; privacy URL and
  video purpose remain. Location changed as described above.
- Retrieved the author-published
  [Smash Balloon entry file](https://plugins.svn.wordpress.org/feeds-for-youtube/trunk/youtube-feed.php)
  and [WP Social Ninja entry file](https://plugins.svn.wordpress.org/wp-social-reviews/trunk/wp-social-reviews.php),
  versions 2.11.1 and 4.4.0. Retained those detection hints.

### Unresolved and impact

The internal `youtube.com/s/player` route was not established as a stable
public integration contract by the API reference; retain the historical match
until a captured player load establishes whether a change is needed. Cookie
presence depends on mode and interaction, and the current schema cannot
express that per-cookie scope. Do not turn the three listed cookies into a
promise that every embed sets exactly those cookies. Empty storage and false
Consent Mode flags are retained without claiming a complete absence of other
storage or consent integrations. No addresses, cookies or plugin hints changed.

## stripe

Outcome: **corrected**, version 2 → 3, with unresolved findings.

### Evidence and changes

- Stripe's current [privacy policy](https://stripe.com/privacy), effective
  April 28, 2026, names transfers including the USA and India. Changed
  `dataCountry` to `USA, India and other countries`. The page announces a
  November 20 update; that future text was not used as current evidence.
- The [privacy center](https://stripe.com/legal/privacy-center) identifies
  Stripe Payments Europe as an EEA contracting entity and lists other
  responsible entities by activity. Retained the existing provider as a
  contracting-provider description, with the scope limitation below.
- Stripe's [cookie settings table](https://stripe.com/cookie-settings)
  confirms the two recorded cookie names, fraud purpose and lifetimes. The
  table was read from page HTML because the web extractor initially omitted
  its rows. Added the direct source; no lifetime was guessed or changed.
- The [domain list](https://docs.stripe.com/ips) contains all five current
  matching hosts. Added it. A server/network allowlist is broader than browser
  detection, so no additional domains were copied into the catalog.
- Added the [advanced fraud detection guide](https://docs.stripe.com/disputes/prevention/advanced-fraud-detection).
  Its coverage and disabling limitations support both existing guidance notes.
- Retrieved the author-published
  [WooCommerce Stripe entry file](https://plugins.svn.wordpress.org/woocommerce-gateway-stripe/trunk/woocommerce-gateway-stripe.php),
  version 11.1.1, and added it as evidence for the existing plugin path.

### Unresolved and impact

The provider field cannot enumerate every controller, processor and regulated
entity by activity. Do not present its one name as the only recipient. The
privacy center documents further optional Link and Elements cookies; the
current two-cookie list is not exhaustive. A generic `m` cookie cannot safely
be attributed to Stripe on name alone, and the schema has no cookie-domain
constraint. Stripe lists storage keys on its own origins as well; do not add
those as though they are always storage on the merchant's origin. A scoped
schema/consumer design and integration evidence are needed before expanding
these detection rules. No payment loading or blocking behavior changed.

## Validation

The ledger accounts for all 210 ids, with four reviewed and 206 pending.

unchanged, each version increased once, existing translations were only
shortened, and the plugin manifest has exactly its original file paths.

Source versions and `checked` dates reflect this review; remaining limitations
are listed above. No release metadata or tags are updated by this review.
